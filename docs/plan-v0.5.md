# 私人音樂平台開發計畫

版本：v0.5｜日期：2026-10-02（Asia/Taipei）｜狀態：需求與架構規劃，尚未開發

## 1. 目標與已確認需求

建立一個統一操作的私人音樂平台：搜尋 BT 資源 → 選擇檔案／版本 → 下載 → 整理 → 上傳 Google Drive → 曲庫播放。

- 支援手動匯入單首、單專輯、混合批次、多層資料夾及 ZIP；辨識不完整也能入庫播放。
- 精確重複音檔去重與專輯收錄分開處理；自動辨識可撤回，不強制合併未知版本。
- 音樂約八成為日本音樂；支援日文原名、別名、專輯版本與合輯整理。
- 長期音檔存放 Google Drive；自有 VPS 保存資料庫、暫存與受限快取。
- 最低支援目標：整台 VM 為 1.5 GB RAM、20 GB 磁碟，單人使用；程式不得把整台容量當成自己的預算，必須替作業系統與其他服務留餘量。
- 操作接近 Spotify／YouTube Music；採 Animeko 同類的 Material 3 介面與來源選擇體驗。
- 後端用 Go；客戶端優先 Kotlin＋Compose Multiplatform＋Material 3。
- aria2 以外部子程序執行，但隨產品打包、自動配置；不用使用者另外安裝設定。
- 可改接外部 aria2、qBittorrent，以及日後新增的下載器。
- rclone 的儲存能力嵌入 Go；不內置整套 Navidrome，不依赖其 UI。
- 資源來源以通用 RSS 管理為核心，提供 Nyaa RSS 範本；不要求每個 BT 站都寫專用適配器。
- 首次仍需使用者授權 Google Drive、設定 RSS 來源與管理員帳號。

「一個程式」指一套產品、統一介面與部署套件；允許主服務管理 aria2 等子程序。Kotlin 客戶端安裝在使用者裝置，Go 服務部署在 VPS。

## 3. 系統架構

| 元件 | 責任 |
|---|---|
| Kotlin 客戶端 | Material 3 UI、播放、歌詞、搜尋、任務管理；Android 優先，桌面後續 |
| Go API 服務 | 認證、曲庫、歌單、歷史、任務調度、串流、外部元件管理 |
| SQLite | 曲庫索引、RSS 來源／條目／去重紀錄、任務狀態、歌單、歷史與設定；保存在 VPS 本地 |
| Go RSS 模組 | 通用 feed 解析、輪詢、關鍵字規則、下載連結識別；特殊站點解析器可選 |
| rclone 儲存模組 | 遠端列檔、上傳、讀取與進度；封裝依賴、固定版本 |
| aria2 子程序 | HTTP／BT 下載與做種；Go 自動配置並經 JSON-RPC 控制 |
| 可選 FFmpeg／標籤工具 | 格式解析、必要時轉碼或 CUE 分軌；驗證後納入打包 |
| Google Drive | 音檔及必要旁附檔案的長期存放 |

不使用 Redis、Elasticsearch 或 FUSE 掛載作為第一版必要依賴。SQLite 搜尋先滿足日文原名與別名；假名／羅馬字模糊搜尋需另做正規化，不假設 SQLite 自動完成。

Go 後端直接從儲存模組取得遠端資料，以本地曲庫索引管理內容。移除 Navidrome 後，串流與快取由本程式負責。

### 通用 RSS 來源管理

- 設定來源名稱、RSS URL、更新間隔、啟停狀態與可選認證；提供 Nyaa RSS 範本，具體 URL、音樂分類及參數在 P0 驗證後固定。
- 來源範本供使用者新增，不強制訂閱或自動下載；不包含站點專用爬蟲作為必要依賴。
- 顯示標題、發布日期、來源、資源連結；大小、做種數、格式等只在 feed 有提供或可可靠解析時顯示，缺少即標示未知。
- 優先識別 enclosure 的 torrent 連結、magnet 和明確下載連結；只有詳情頁連結的條目不得假裝可直接下載，可開啟來源或用選配解析器補充。
- 支援手動刷新與定時輪詢；預設建議每 30 分鐘，尊重來源限制、錯誤退避並錯開輪詢時間。
- 搜尋預設是在已取得的 RSS 條目中篩選；只有來源支援搜尋 RSS 時才提供站內搜尋，不能保證 RSS 可查完整歷史或分頁。
- 規則提供標題關鍵字包含／排除。預設手動選下載；自動下載必須由使用者啟用，首次訂閱先建立基準，不自動抓取全部舊條目。
- 去重保存來源＋GUID、正規化資源連結，以及可取得的 infohash；不同来源的同一種子可合併，不按相同標題直接合併不同版本。
- 自動下載與手動下載共用任務佇列和 2 GB 暫存配額；大小未知時先取 torrent metadata，再做容量檢查。
- 限制 feed 回應大小、解析條目數、輪詢並行與保留歷史；RSS 資料也計入 500 MB 初始資料預算。
- Prowlarr 不是第一版必要元件；特殊解析器或外部索引服務只作未來擴充。

## 4. 入庫與任務設計

建議狀態：待處理、下載中、整理中、待確認、上傳中、驗證中、已入庫、失敗、暫停、取消。做種狀態獨立保存，避免與入庫完成混淆。

1. 從 RSS 條目挑選或手動加入資源，取得可用檔案資訊，估算磁碟需求。
2. 使用者挑選專輯、版本及檔案；metadata 未取得前不承諾容量足夠。
3. 下載至 VPS 暫存，原檔作為做種資料。
4. 本地解析音檔與標籤，逐檔整理，避免全包複製。
5. 如需改寫音檔，對該檔建立整理副本；不修改做種原檔。
6. 上傳 Drive，保存遠端 file ID、大小及可用校驗資訊。
7. 驗證遠端檔案後，以資料庫交易發布曲庫項目。
8. 整理副本按政策清理；做種原檔依保留規則處理。

任務與進度持久化，重新啟動後能恢復或安全重試；重新上傳前對帳，避免產生重複遠端檔案。失敗、尚未驗證的檔案不得當作成功資料清理。

外部下載器若在使用者電腦：VPS 的 localhost 不代表該電腦。必須設計可達連線及完成檔案轉移；優先以可選本地代理主動連回服務、上傳 Drive 並回報結果。僅設定 RPC 位址不足以完成入庫。

### 手動上傳與共用匯入流程

手動上傳與 BT 下載共用解析、去重、上傳驗證與入庫模組，但手動匯入不具有做種原檔保留需求。流程：選擇檔案 → 解析／分組預覽 → 可選修正 → 精確去重 → 上傳 Drive／重用既有音檔 → 入庫。

| 輸入 | 匯入行為 |
|---|---|
| 不同專輯與歌手的混合音檔 | 按原標籤分組，必要時以路徑輔助；不確定項目待整理，不全部合成一張專輯 |
| 單張專輯 | 可選「作為同一專輯」，批次設定專輯、專輯歌手、年份、封面、碟號與曲序 |
| 單首音檔 | 有可靠專輯資料則歸入對應版本；沒有則作為獨立歌曲，不捏造專輯資料 |
| 資料夾／多層資料夾 | 遞迴列出音檔，保留相對路徑；可選「每個子資料夾是一張專輯」並预覽結果 |
| ZIP | 列出內容，處理可用音檔、封面與歌詞；逐檔解壓、上傳、清理，受壓縮檔與解壓暫存總量限制 |

- 分組證據優先序：原始音檔標籤 → 資料夾結構 → 檔名推測 → 使用者修正；外部辨識是可選建議，不覆蓋原資料。
- 分組考慮專輯名稱、專輯歌手、碟號、版本與來源資料夾；不能只按歌曲歌手拆分 OST／合輯，也不能只按同名專輯跨批次盲目合併。
- 預覽顯示歌曲／專輯數、缺失資料、可能重複與匹配差異，支援合併／拆分、日文名稱、封面與批次修正。
- 每批有持久化進度；部分成功、部分失敗分開呈現，可逐檔重試，整批不必全部成功才能播放已入庫歌曲。
- 大批檔案採分批列舉、分批預覽及逐檔傳輸；不把所有音檔／封面載入 RAM。每檔驗證遠端成功後可清理暫存，整批總容量可以超過 2 GB，但同時占用不能超額。
- ZIP 必須計入壓縮檔本體、正在解壓檔案及修改副本。不能假設逐檔解壓就讓任意大小 ZIP 可在 VPS 處理；超額 ZIP 由桌面客戶端／本地代理解壓後逐檔傳送，或提示先解壓再多選上傳。
- 檢查解壓實際總量、單檔大小、項目數、展開比例與輸出路徑，拒絕路徑逃逸；不在 RAM 整包解壓。
- Android／桌面的資料夾選擇、遞迴權限與 ZIP 解壓能力在 P0 驗證；不能假設各平台檔案選擇器相同。

### 音檔、歌曲版本與專輯收錄模型

| 層級 | 保存內容 |
|---|---|
| 音檔資產（asset） | 內容雜湊、大小、格式、Drive file ID、驗證狀態；相同位元組內容可共用一份儲存 |
| 歌曲／錄音版本（track） | 曲名、演唱者、錄音／現場／重錄／混音版本；音檔格式版本可另建關聯 |
| 專輯收錄（album entry） | 專輯版本、track、asset、碟號、曲序、收錄專屬標籤、封面及可用歌詞 |

收錄專屬資訊存資料庫，不為了另一張專輯去改写共用音檔。獨立歌曲允許沒有專輯收錄；歌曲、專輯收錄與音檔各自有穩定 ID。歌單條目可保留選定專輯收錄／音檔版本；播放紀錄保留 track ID 和當時播放的收錄／音檔資訊，避免合併或搬移後失去來源。

| 重複情境 | 預設政策 |
|---|---|
| 相同音檔再次上傳，且專輯收錄也相同 | 重用驗證成功的 asset，略過重複收錄；不重複存 Drive |
| 相同音檔需要收錄到另一張專輯 | 只共用 asset，另建專輯收錄，保留不同封面與曲序 |
| 相同歌曲出現在原專輯／精選輯 | 保留兩張專輯；只有音檔內容確實相同才共用資產 |
| 同名歌曲但現場／重錄／混音不同 | 保留不同錄音版本；不能靠標題、歌手或時長直接合併 |
| 同錄音但 FLAC／MP3 或音檔內標籤不同 | 位元組雜湊不同，僅列可能重複；預設保留、不自動替換 |

- 上傳／接收時逐段計算 SHA-256 與大小；伺服器驗證計算結果，不只信任客戶端提供的雜湊。小 VPS RAM 不需容納完整檔案。
- 精確去重鍵使用内容雜湊＋大小；並行匯入以唯一约束／任務鎖處理。可用的遠端校驗資訊用於傳輸驗證，不必等同本地 SHA-256。
- 同檔案再次匯入的原資料可能不同，保留本次匯入意圖與原始標籤供預覽；不因檔案已存在就丟掉另一張專輯收錄。
- 每次新增收錄仍判斷是否相同版本／曲序，無法確定時讓使用者選擇「略過／新增收錄／保留另一版本」；替換是明確操作並顯示影響範圍。
- 音訊指紋或外部錄音 ID 可作未來辨識輔助，不是第一版自動刪除依據。
- 刪除一個專輯或收錄只解除關聯；asset 仍被其他收錄、獨立歌曲或任務引用時不刪除遠端音檔。

### 辨識錯誤、未知資料與撤回

| 模式 | 行為 |
|---|---|
| 保留原資料（預設） | 用原標籤及路徑，缺失欄位用明確未知值；不查外部資料、不自動改寫音檔 |
| 輔助辨識 | 顯示候選與原資料差異，使用者確認後套用；低信心不自動修改 |
| 直接匯入、稍後整理 | 先入庫播放，保留原檔名／路徑；「待整理」是提示而非播放門檻 |

- 保存原始標籤、檔名、相對路徑、來源、候選資料及套用變更；未知不得當成已確認匹配。
- 批次操作：取消本批辨識結果、恢復原標籤／資料夾分組、指定子資料夾為專輯、統一修正欄位；不要求逐首確認才能聽歌。
- 自動辨識建議可撤回；只撤回其實際修改欄位，已被使用者後續編輯的衝突欄位需提示，不能無條件覆蓋新修改。
- 音檔本體預設不改寫，優先保存資料庫覆寫標籤；需要修改／匯出音檔時另行確認並保留可恢復原資料。
- 預設原則：精確相同音檔才自動去重；未知或相似版本先保留；辨識失敗不阻止播放。

## 5. 曲庫、串流、快取與紀錄

### 曲庫掃描

- 新增檔案在上傳前解析，避免再从 Drive 重複下載讀標籤。
- 增量更新，以內部 track ID 保留歌曲身份，檔名或路徑變動不直接刪除歷史。
- 利用 Drive Changes API 對帳外部變更；首次已有 Drive 曲庫需分批掃描。
- 遠端暫時不可達標記狀態，不當成永久刪除。
- 以多階段、小佇列、固定 worker 處理；封面解碼設定尺寸與輸入限制。

### 串流與快取

- 支援 HTTP Range、取消請求及內容版本驗證；優先原格式播放。
- 本地完整檔案可用 Go ServeContent；遠端以可定位讀取或 Range 轉送配合快取。
- 音檔快取放 SSD；RAM 不保存整首音檔或整個曲庫。
- 第一版先完成按需串流與有容量限制的檔案快取；分塊快取的必要性由驗證決定。
- 同一內容請求共用拉取工作；避免預載、播放和上傳產生多份無用副本。
- 快取以 file ID＋內容版本識別；淘汰久未使用項目，活動中的檔案保留。
- 預載最多下一首，低磁碟時停用。轉碼預設關閉；選擇啟用時最多一路，須另驗證資源需求。

### 歌單與播放紀錄

- 歌單條目有獨立 ID、track ID、可選專輯收錄／音檔版本及排列位置；允許重複歌曲。
- 客戶端上報 session ID、實際播放時間、位置、暫停／結束；服務端去重。
- 明確定義「計一次播放」的時長門檻；不能由音檔 HTTP 請求數推算。
- 位置更新節流，離線事件可補送；歷史保留與備份策略可配置。

### 日本音樂整理

- 日文原名與別名分開保存，不強制羅馬字覆蓋。
- 區分歌手、專輯歌手、社團、作品、曲名與版本；避免 OST／合輯散成多個錯誤專輯。
- 多碟、重發、限定版、不同音質均有可識別版本。
- 同人／特典等無外部資料庫記錄的專輯仍可手動入庫。
- 該類音樂的實際比例、CUE／整軌 FLAC／壓縮包需求尚待確認。

### 候選辨識方案與 API 要求（待決定）

以下只記錄候選方案，不代表已決定採用或啟用。建議流程是原標籤／資料夾優先，MusicBrainz 按需補全專輯，普通查詢失敗再可選使用 Chromaprint＋AcoustID，最後允許人工／批次整理。Go 整合必要能力並參考 Picard／beets；是否打包 beets 未定，不把它當必要依賴。

| 能力 | 帳號／key 要求 |
|---|---|
| 讀原標籤、資料夾分組、SHA-256 去重 | 不需要，完全本地處理 |
| MusicBrainz 公開歌手／歌曲／專輯查詢 | 不需要 API key 或登入；需有效 User-Agent，每應用最多每秒 1 次請求 |
| Chromaprint 本地計算指紋 | 不需 key／帳號；需 fpcalc 或對應函式庫與解碼能力 |
| AcoustID 線上指紋辨識 | 需註冊應用取得 application key，傳入 client；一般使用者無需各自登入 |
| AcoustID 提交新指紋 | 除 application key，另需使用者登入取得個人 user key；不列入第一版 |
| MusicBrainz 提交資料／使用者私有資料 | 需認證；不列入基礎查詢範圍 |

候選配置方式：VPS 管理員設定一次 AcoustID application key；未配置則停用線上指紋辨識，原標籤整理、上傳、入庫和播放仍可用。不能使用官方範例測試 key 作正式配置。key 的最終提供方式待決定。

- AcoustID 公共服務最多每秒 3 次請求；共用限流、快取與錯誤退避。
- MusicBrainz／AcoustID 公共免費服務適用非商業用途；商業化需重新確認服務條款。
- 外部查詢在使用者選擇補全／辨識模式後才執行；說明會送出的標籤、指紋與時長資料，指紋查詢不要求上傳整份音檔。
- 指紋按需執行，僅一個背景 worker，結果快取；不強制掃描全部歌曲。工具子程序占用也算進 ≤500 MB 尖峰設計目標，必須實測；客戶端／本地代理計算可作候選。
- 匹配分數高仍不直接覆寫原資料，不以音訊指紋自動刪除疑似重複版本。
- 選型、工具打包與 API 設定後續再決定，現在不新增必要帳號設定門檻。

#### 準確率驗證

未找到可以直接套用本曲庫的 Picard／beets／AcoustID 通用或日本歌曲獨立公開準確率，不能預設 90% 等數字。匹配相似度不等於經校準的正確機率；錄音辨識正確也不代表專輯／限定版／精選輯收錄版本正確。

建議用使用者提供或授權的 200–500 首已知正確資料歌曲，按實際曲庫的 J-pop、動畫歌曲／OST、同人／東方、Vocaloid 等分類；分別測試保留原標籤與移除標籤。測試集與執行方式待決定。

分開報告：候選命中率（有候選／全部）、候選中錄音正確率（正確／有候選）及全樣本錄音成功率（正確／全部）、專輯版本配對正確率、高分錯配率、未知比例，以及每首耗時、CPU／RAM 峰值、API 請求數。結果只代表樣本，依實測再決定方案及任何自動套用門檻。原資料優先、未知可播放、辨識可撤回仍為既定政策。

## 6. 1.5 GB RAM／20 GB 磁碟支援目標

以下為容量設計與验收目標，不是實測或資源使用保證。

### 並行預設

| 工作 | 預設 |
|---|---|
| 活躍 BT 下載 | 1；做種亦納入總連線與資源限制 |
| Drive 上傳 | 1 |
| 解析／封面處理 | 1 worker |
| 轉碼／分軌 | 預設關閉；啟用後最多 1，重型工作排隊並重新驗證資源需求 |
| 播放 | 單人一路為基準 |
| 預載 | 最多下一首 |

程序合計 RAM 目標：常態 150–300 MB，尖峰目標不超過 500 MB。包含 Go／rclone、aria2 及啟用的工具子程序；作業系統、其他服務與可回收檔案快取另外計算，不能將剩餘 RAM 預設視為本程式可用。使用者客戶端 RAM 不算 VPS 用量。這是待實測的設計目標，不是硬上限保證；超大圖片、BT peers、轉碼需單獨限制，Go 記憶體設定不等於整套程序限制。

### 程式自身磁碟預算

| 用途 | 預設預算 |
|---|---:|
| SQLite、縮圖、歌詞、輪替日誌 | 初始目標不超過 500 MB |
| 播放快取 | 512 MB，可調低 |
| 下載、整理、做種總暫存 | 2 GB，共用配額 |
| 程式檔案與隨附工具 | 另計，打包後實測 |
| 整套程式磁碟占用 | 目標約 3–4 GB，包含上述項目；非實測保證 |

20 GB 是整台 VM 的磁碟規格，不為本程式分配全部 20 GB。作業系統與其他服務占用不屬於上表；部署前按實際剩餘空間縮減配額，預設為整個檔案系統保留至少 4 GB 可用空間，可由管理員調整。若保留門檻無法滿足，暫停新下載與非必要寫入並顯示原因。

資料庫與封面增長需監測；500 MB 為初始容量預算，不允許滿額後直接刪除必要資料。可減少縮圖、輪替日誌，仍不足時需由使用者調整配額或縮減曲庫。程式更新、資料庫備份及套件解壓的短暫額外空間也要預留。

- 開始任務前為選取資料、修改副本、解壓或分軌預留空间。
- 快取配額與下載預算共用磁碟檢查，避免各自以為有足夠空間。
- 低空間：清理可淘汰快取 → 停止預載 → 暫停／拒絕新任務；保護未上傳資料。
- 超過 2 GB 暫存預算的 BT 包：選部分檔案、分批處理，或使用外部下載器；不得為了下載自動吃滿 VM 磁碟。
- 上傳完成不等於可以刪除做種資料；保留規則由使用者設定，受磁碟總預算限制。
- 第一次全曲庫掃描也需受限，不讓掃描填滿快取。

## 7. UI 與部署

導覽：首頁、搜尋、曲庫、任務、設定；曲庫提供「匯入音樂」入口及批次預覽／待整理頁。手机底部導覽與迷你播放器；桌面側邊導覽與較寬的歌曲／歌詞區。

搜尋分為「我的曲庫／RSS 資源」；來源頁可加入 RSS、套用 Nyaa 範本、設定更新及規則；專輯詳情呈現版本及來源；下載、上傳、入庫進度出現在同一任務頁。

部署套件隨附 Go 主服務與對應 OS／架構的 aria2；主服務自動建立設定、RPC 密鑰、資料目錄並管理健康檢查、啟停、退出及重啟退避。Linux VPS 優先；是否提供單一 Docker 映像或原生套件尚待決定。

Google OAuth、下載器憑證保存在服務端並限制讀取；內附 aria2 RPC 僅綁 loopback。對外提供統一登入與 HTTPS。備份至少包含 SQLite、設定和遠端檔案索引；Drive 音檔不能替代歌單／歷史資料庫備份。

## 8. 開發階段與驗收

| 階段 | 交付與驗收 |
|---|---|
| P0 技術驗證 | Go 嵌入 rclone 的授權、上傳、讀取；aria2 打包/RPC；FLAC/MP3/M4A 解析、SHA-256 去重、檔案／資料夾權限與 ZIP 容量驗證；Drive Range 拖曳播放；Nyaa 範本與通用 RSS 連結解析；在 1.5 GB／20 GB 环境測試 |
| P1 最小閉環 | 手動 magnet／torrent → 選檔 → 下載 → 解析 → 上傳驗證 → 入庫 → 播放；單首／多檔手動匯入共用流程；初始化與任務頁 |
| P2 日常可用 | RSS 管理／輪詢／去重／關鍵字規則與可選自動下載、專輯／資料夾／ZIP 批次匯入與分組預覽、共用音檔／跨專輯收錄、辨識模式與撤回、歌單、收藏、歌詞、歷史、日文別名、增量對帳、低磁碟管理、重啟恢復 |
| P3 擴充與發布 | qBittorrent／本地代理、桌面客戶端、必要轉碼／分軌、升級與備份恢復；可重現部署包 |

匯入功能驗收包括：同檔案上傳兩遍只建立一份可用遠端資產；同檔案跨專輯保留獨立收錄；不同錄音版本不因同名被合併；標籤不同的檔案只提示可能重複；撤回辨識不覆蓋後續人工修正；未知單首可播放；混合批次可分組／拆分；ZIP 超配額與路徑逃逸被拒絕；刪除單一專輯不刪除仍被引用的共用音檔。

最低配置驗收包括：待機、連續播放、拖曳進度、播放同時下載／上傳／入庫、首次分批掃描、低磁碟、Drive 中斷、程序意外退出與恢復。記錄程序 RSS、系統可用 RAM、CPU、磁碟峰值、首次播放延遲及 Drive 請求量。驗收以整套程序常態 150–300 MB、尖峰目標 ≤500 MB，以及磁碟目標約 3–4 GB 為基準；驗證時不得獨占 VM 剩餘資源。限制內不得 OOM、丟失未驗證音檔、重複計播放或破壞做種原檔。超過容量的任務須在可預測時間內拒絕或暫停並說明原因。
